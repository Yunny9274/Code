# GECo-CF server guide

This guide starts with a read-only preflight. Do not run the pilot until the
frozen dataset and checkpoint have been identified and the adapter has been
completed.

## Step 1: preflight the server

Upload the whole `geco_cf/geco_cf` directory to the server, then run:

```bash
cd /path/to/geco_cf/geco_cf
python scripts/server_preflight.py --json
```

If the repository is not yet on the server, upload it first. The command does
not install packages, change files, or start a training job. It reports:

- Python and operating-system versions;
- whether `nvidia-smi` sees a GPU;
- installed versions/import status for `geco-cf`, NumPy, NetworkX, PyTorch,
  and PyG;
- PyTorch CUDA build, CUDA availability, device count, and device names.

Send the complete JSON output back before installing or changing the server
environment. In particular, do not guess a PyTorch wheel from the CUDA driver:
the PyTorch CUDA build and the PyG wheels must be compatible.

## Step 2: create or select the ML environment

The first reviewed server profile is Python 3.10 on Linux, NVIDIA driver
535.146.02, and two RTX 3070 GPUs. For this profile, use a fresh environment
with PyTorch 2.3.1 CUDA 12.1 and PyG 2.5.3. CUDA 12.1 is supported by this
driver and avoids relying on a newer system CUDA toolkit.

Create the environment from the project root:

```bash
conda create -n geco-cf python=3.10 -y
conda activate geco-cf
python -m pip install --upgrade pip setuptools wheel
python -m pip install numpy==1.26.4 networkx==3.3 pytest==8.3.5
python -m pip install torch==2.3.1 --index-url https://download.pytorch.org/whl/cu121
python -m pip install torch-geometric==2.5.3
python -m pip install -e . --no-deps
```

Do not run `pip install -e '.[pyg]'` blindly on a CUDA server: its broad
version ranges may replace a working CUDA build. If PyTorch is not installed,
install the exact command generated by the official PyTorch selector for the
server's CUDA version first, then install a matching PyG build. Verify with:

```bash
python -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.is_available())"
python -c "import torch_geometric; print(torch_geometric.__version__)"
CUDA_VISIBLE_DEVICES=0 python -c "import torch; print(torch.cuda.get_device_name(0)); print(torch.ones(1, device='cuda'))"
python -m pytest
python scripts/server_preflight.py --json
```

The local tests are CPU-only and should still report `5 passed` on the server.
The GPU check must print `NVIDIA GeForce RTX 3070` and a CUDA tensor. Keep
`CUDA_VISIBLE_DEVICES=0` for the first pilot; the workloads are per-graph and
do not need multi-GPU execution.

## Step 3: reproduce the frozen BA2Motifs model

Run the reproducible training entry point supplied in this repository:

```bash
CUDA_VISIBLE_DEVICES=0 python scripts/train_ba2motifs.py \
  --data-root data/BA2Motif \
  --output-dir checkpoints/ba2motifs_seed0 \
  --seed 0 \
  --device cuda:0
```

It creates `model.pt`, `split.json`, and `train_manifest.json`. The default
split is stratified 80% train, 10% validation, and 10% test. The validation
checkpoint is frozen before test evaluation. Record:

```text
dataset name/version and split
number of test graphs and test graph IDs
model architecture and checkpoint path
test accuracy and checkpoint SHA256
node feature dimension and number of classes
torch/torch-geometric versions
```

Use the same preprocessing and checkpoint for every method. The pilot keeps
the model frozen and requires a predictor returning one-dimensional,
pre-softmax class logits.

The real adapter is now `examples.ba2motifs_adapter:build_experiment`; it loads
the saved checkpoint and exact test IDs. Do not use the old template adapter.

## Step 4: smoke run after adapter completion

Once the adapter is filled in, run only ten eligible test graphs first:

```bash
python scripts/run_pilot.py \
  --config configs/pilot_ba2motifs_smoke.json \
  --factory examples.ba2motifs_adapter:build_experiment \
  --output-dir results/pilot_ba2motifs_seed0_smoke
python scripts/validate_pilot.py \
  --input-dir results/pilot_ba2motifs_seed0_smoke
python scripts/analyze_pilot.py \
  --input-dir results/pilot_ba2motifs_seed0_smoke \
  --output results/pilot_ba2motifs_seed0_smoke/analysis.json
```

For the smoke run, temporarily set `"max_graphs": 10` in a copied config;
keep the committed config unchanged. Check that:

- every eligible graph is originally classified correctly;
- `summary.json` has nonzero graph and community counts;
- `edges.csv` is populated;
- forward calls equal `1 + number_of_communities + number_of_edges` per graph;
- no NaN values or traceback occurs.

Send back the command, accuracy, `summary.json`, and validator output. Only
after this smoke run passes should the full test split be launched.

## Step 5: full pilot and seeds

Run seeds 0, 1, and 2 in separate output directories. Keep the checkpoint,
split, eligible graph IDs, `alpha=0.5`, Louvain method, and `top_k_edges=5`
fixed. The pilot's go/no-go evidence is:

- top-community margin drop versus Random and Largest;
- top-community flip rate versus both controls;
- top-community coverage of the global best and top-five individual edges;
- Spearman correlation between community score and best single-edge drop.

Do not implement the full optimizer or tune test-set settings until these
pilot summaries are available.
